# ANU Treasure Map 최종 게임 기획안

문서 상태: 작업 초안 v0.9  
작성 기준일: 2026-05-07 AEST  
작성 목적: 다음 개발/콘텐츠 팀이 ANU Treasure Map의 최종 게임 형태를 이해하고, 현재 구현된 Week 1 프로토타입을 확장 가능한 정식 게임 구조로 이어받을 수 있도록 한다.

## 1. 한 줄 정의

ANU Treasure Map은 플레이어가 ANU에서 14주짜리 한 학기를 보내며 친구, 추억, 장소, 보물을 발견하고, 자신의 선택으로 완성된 하나의 캠퍼스 이야기를 마지막에 회고하는 싱글플레이 내러티브 탐험 게임이다.

## 2. 디렉터 비전

이 게임의 목표는 플레이어에게 모든 보물을 모으라고 요구하는 것이 아니다. 플레이어가 제한된 시간, 에너지, 돈 안에서 어떤 장소를 방문하고, 누구와 시간을 보내고, 어떤 순간을 자기 것으로 남길지 선택하게 만드는 것이다.

플레이어에게 ANU 캠퍼스는 처음에는 낯선 지도처럼 보인다. 하지만 14주가 끝날 때, 그 지도는 자신이 뛰었던 코트, 누군가와 대화했던 벤치, 우연히 발견한 동물, 놓쳤지만 기억에 남은 행사, 다른 사람에게 남긴 힌트로 채워진다. 최종 결과물은 승패 화면이 아니라 "내가 ANU에서 어떤 학기를 보냈는가"를 보여주는 개인화된 회고록이다.

핵심 감정은 다음과 같다.

- ANU 캠퍼스가 친근해졌다.
- 나만의 대학 생활을 만든 느낌이 든다.
- 숨겨진 장소를 발견한 탐험감이 있다.
- 친구들과 연결된 따뜻함이 있다.
- 다시 플레이하면 다른 길이 열릴 것 같다.

## 3. 플레이어 정체성

플레이어는 ANU 학생이다. 주 대상은 ANU 신입생이지만, 재학생, 교환학생, 예비 학생, ANU에 관심 있는 방문자도 게임의 의미를 이해할 수 있어야 한다.

신입생에게 이 게임은 낯선 캠퍼스를 익숙하게 만드는 안내자다. 재학생에게는 이미 지나치던 장소 안에 숨어 있던 이야기와 의미를 다시 보게 만드는 장치다. ANU에 관심 있는 사람에게는 캠퍼스 안에서 실제로 어떤 삶과 관계가 생기는지 상상하게 만드는 창이다.

## 4. 게임의 최종 목적

플레이어는 14주 동안 ANU 캠퍼스를 탐험하며 장소, 친구, 이벤트, 보물을 경험한다. 여기서 14주는 학기 시작부터 학기 종료까지를 압축한 한 학기를 의미하며, 7-8주차의 teaching break도 포함한다. 게임 종료 시 시스템은 플레이어가 어떤 장소를 방문했고, 어떤 선택을 했고, 어떤 보물을 수집하거나 공유했으며, 어떤 친구와 연결되었는지를 회고 형식으로 보여준다.

도감 완성은 보조 목표다. 이 게임의 최종 목적은 모든 보물을 수집하는 것이 아니라, 플레이어의 선택으로 서로 다른 캠퍼스 이야기를 완성하는 것이다.

## 5. 디자인 기둥

### 5.1 캠퍼스는 지도이자 기억의 구조다

장소는 단순한 이동 노드가 아니다. 각 장소는 학생 생활, 역사, 자연, 시설, 사람, 소문, 행사, 계절의 경험을 담는 이야기 단위다.

### 5.2 보물은 물건보다 의미다

보물은 반드시 물리적 사물일 필요가 없다. 보물은 장소, 경험, 학생 문화, 역사적 흔적, 자연 현상, 친구와의 사건, 클럽 활동, 유저가 남긴 이야기일 수 있다.

### 5.3 선택은 회고에 남아야 한다

플레이어의 선택은 즉시 보상뿐 아니라 게임 종료 회고에 반영되어야 한다. 수집, 공유, 놓침, 도움, 우회, 재방문 같은 선택이 마지막에 다시 의미를 가져야 한다.

### 5.4 모든 것을 한 번에 볼 수 없어야 한다

14주 안에 모든 보물을 볼 수 없도록 설계한다. 그래야 플레이어의 학기가 서로 달라지고, 다시 플레이할 이유가 생긴다. 이 게임에서 미완성 도감은 실패가 아니라, 플레이어가 한 학기 동안 어떤 삶을 선택했는지 보여주는 여백이다.

### 5.5 나눔은 손해가 아니라 유산이다

보물을 공유하면 이번 회차의 도감에는 수집되지 않지만, 다른 플레이어에게 힌트로 남는다. 이 선택은 엔딩에서 이타적인 legacy로 해석되어야 한다.

## 6. 현재 구현 기준선

현재 저장소의 Godot 프로젝트는 정식 게임 전체가 아니라 Week 1 vertical slice에 가깝다. 다음 팀은 이 범위를 "현재 구현"으로 고정하고, 아래의 최종 설계를 확장 목표로 삼아야 한다.

현재 확인된 구현 기준은 다음과 같다.

- 게임은 Godot 프로젝트로 구현되어 있다.
- 현재 구현의 최대 주차 값은 16주로 설정되어 있다. 최종 설계에서는 이를 14주로 수정해야 한다.
- 현재 주요 자원은 시간이며, 돈은 상태값과 HUD에 존재한다.
- 현재 `Global.time` 기본값은 8이고, 이동은 그래프 edge당 시간 1을 소비한다.
- 현재 `Global.money` 기본값은 50이다.
- 현재 `stamina` 값은 존재하지만 최종 에너지 시스템으로 완성되어 있지는 않다.
- 현재 위치 데이터는 19개 location id를 포함한다.
- 현재 이벤트 데이터는 22개 event record를 포함하며, 이 중 20개가 enabled 상태다.
- 현재 이벤트는 위치, 시간대 조건, clue 보유 여부, random trigger chance, choice outcome, treasure found, re-trigger 여부를 사용한다.
- 현재 보물 발견 후 `Collect` 또는 `Share` 버튼을 보여주는 popup UI가 존재한다.
- 현재 공유한 보물은 로컬 save data의 `shared_treasure_records`에 저장되고, in-game social media feed에 shared post 형태로 재구성된다.
- 현재 외부 Supabase 기반 비동기 공유는 최종 설계 대상이며, 현재 로컬 구현은 그 개념을 증명하는 프로토타입이다.

## 7. 최종 게임 흐름

### 7.1 전체 흐름

1. 플레이어는 온보딩에서 이름, 전공, 기본 프로필을 정한다.
2. 전공 또는 시작 선택에 따라 초기 trait를 얻는다.
3. 각 주의 시작에 플레이어는 이번 주에 함께 탐험할 친구를 최대 2명 선택한다.
4. 친구들은 trait와 clue source 역할을 한다.
5. 플레이어는 ANU 지도에서 장소를 선택해 이동한다.
6. 이동과 탐험은 시간과 에너지를 소비한다.
7. 이벤트 선택지는 시간, 에너지, 돈, trait, 친구 여부에 따라 잠기거나 열릴 수 있다.
8. 이벤트 결과로 보물 발견, clue 획득, 친구 추가, 자원 변화, missed memory, 재방문 가능성이 발생한다.
9. 보물을 발견하면 플레이어는 collect 또는 share를 선택한다.
10. 14주가 끝나면 Memory Recap과 개발자 credit을 보여준다.

### 7.2 핵심 반복 루프

주간 시작 -> 친구 선택 -> 인스타그램/clue 확인 -> 지도 이동 -> 장소 탐험 -> 이벤트 선택 -> 결과 저장 -> 자원 소모 -> 다음 장소 또는 다음 주 -> 14주 후 회고

## 8. 지도와 장소 구조

### 8.1 현재 지도 구조

현재 구현은 ANU 캠퍼스를 location node와 neighbor connection으로 표현한다. 각 location id는 하나의 지도 지점이며, 플레이어는 연결된 node 사이를 이동한다. 이 구조는 Week 1 vertical slice에서는 충분히 명확하고 구현 부담이 낮다.

### 8.2 최종 지도 확장 방향

최종 게임에서 이벤트 수와 장소 밀도가 늘어나면, 단일 node만으로는 장소의 의미와 세부 이벤트를 모두 담기 어렵다. 따라서 장기적으로는 캠퍼스를 큰 구역과 세부 노드로 나누는 계층형 지도 구조를 권장한다.

예시 구조:

| 계층 | 역할 | 예시 |
| --- | --- | --- |
| Region | 캠퍼스의 큰 생활권 또는 탐험 구역 | Central Campus, Residential Area, Sports Area, Arts Area |
| Location Node | 지도에서 이동 가능한 주요 장소 | Chifley & Marie Reay, Bruce Hall, Copland |
| Sub-node | 특정 장소 안의 세부 탐험 지점 | notice board, rooftop garden, basketball court, cafe corner |
| Event Anchor | 이벤트가 실제로 발동되는 지점 | 특정 벤치, 안내판, 코트, 건물 입구 |

이 구조를 쓰면 같은 큰 장소 안에서도 시간대, 친구, clue, 선택 상태에 따라 다른 세부 이벤트를 열 수 있다. 예를 들어 Bruce Hall이라는 location 안에 grassland, entrance, rooftop garden, nearby path 같은 sub-node를 둘 수 있다.

### 8.3 시간 기반 접근성

최종 게임에서는 시간에 따라 접근 가능한 장소나 이벤트가 달라질 수 있다.

접근 제한은 우선 location 단위에 둔다. 예를 들어 특정 건물이나 시설이 저녁 이후 닫혀 있다면, 해당 location 자체를 그 시간대에 접근 불가능하게 처리한다. 추후 sub-node 구조가 구현되면 같은 location 안에서도 특정 sub-node만 시간대별로 열고 닫는 방식으로 확장할 수 있다.

예시:

- 아침에는 카페, 무료 아침 식사, 수업 전 만남 이벤트가 잘 열린다.
- 점심에는 중앙 캠퍼스, 푸드 코트, 동아리 홍보, 친구 만남 이벤트가 잘 열린다.
- 저녁에는 기숙사, 스포츠, 클럽, 야간 산책, 공연 관련 이벤트가 열린다.
- 일부 행정/건물/시설 이벤트는 특정 시간 이후 접근이 제한될 수 있다.
- 자연, 공공 예술, 야외 장소는 상시 접근 가능하되, 시간대별 묘사가 달라질 수 있다.

주의:

- 시간 제한은 플레이어를 막기 위한 장벽이 아니라, 캠퍼스가 시간에 따라 다른 얼굴을 가진다는 느낌을 주기 위한 장치여야 한다.
- 이벤트 데이터는 location 접근 시간과 충돌하면 안 된다. 특정 시간대에 접근할 수 없는 location에는 그 시간대에만 발생하는 이벤트를 배치하지 않는다.
- 너무 많은 장소를 닫으면 탐험 흐름이 답답해지므로, 항상 갈 수 있는 fallback 장소와 저비용 행동이 필요하다.

## 9. 자원 시스템

최종 게임은 시간, 에너지, 돈 세 자원을 사용한다.

### 9.1 시간

시간은 한 주 안에서 가장 회복 불가능한 자원이다. 이동, 탐험, 이벤트 선택에 사용된다. 시간은 특정 이벤트로 회복되지 않는다. 시간이 모두 소진되면 해당 주가 종료된다.

현재 구현은 단순한 8 AP 모델을 사용한다. 최종 게임에서는 한 주 전체를 실제 7일로 나누지 않고, 그 주의 자유시간을 대표하는 하루로 압축한다. 이 대표 하루는 08:00부터 24:00까지 진행되며, 플레이어의 행동은 1시간 단위로 시간을 소비한다. 현재 시간은 이벤트 조건과 장소 접근성에 영향을 준다.

이 구조에서 한 라운드는 "그 주에 플레이어가 ANU에서 어떻게 시간을 보냈는가"를 상징하는 하루다. 수업, 과제, 생활 루틴 전체를 시뮬레이션하는 것이 아니라, 플레이어가 자유롭게 캠퍼스를 탐험할 수 있었던 핵심 시간만 게임화한다.

권장 시간대:

| 시간대 | 범위 | 설계 역할 |
| --- | --- | --- |
| Morning | 08:00-11:00 | 등교, 아침 식사, 조용한 캠퍼스, 준비 이벤트 |
| Midday | 12:00-13:00 | 점심, 학생 지원, 친구 만남, 동아리 홍보 |
| Afternoon | 14:00-17:00 | 수업 후 탐험, 도서관, 야외 활동, 발견 이벤트 |
| Evening | 18:00-21:00 | 클럽, 스포츠, 공연, 기숙사 주변 이벤트 |
| Late Night | 22:00-24:00 | 제한된 야간 이벤트, 귀가, 마감, 조용한 회고 |

이벤트 시간 조건:

| 조건 | 의미 |
| --- | --- |
| morning_only | 아침에만 발생 |
| midday_only | 점심 시간에만 발생 |
| afternoon_only | 오후에만 발생 |
| evening_only | 저녁에만 발생 |
| late_night_only | 밤늦게만 발생 |
| daytime | 08:00-17:59 사이 발생 |
| after_dark | 18:00 이후 발생 |
| anytime | 시간과 관계없이 발생 |

행동 시간 비용 예시:

| 행동 | 시간 비용 |
| --- | --- |
| 인접 location 이동 | 1시간 |
| 같은 region 안의 sub-node 이동 | 보통 시간 소비 없음, 탐색/이벤트 비용에 포함 |
| 다른 region으로 이동 | 1시간, 장거리 이동은 필요 시 2시간 |
| 짧은 탐색 | 1시간 |
| 일반 이벤트 | 1시간 |
| 긴 이벤트/클럽 활동 | 2시간 |
| 휴식 | 1시간 |

24:00이 되면 현재 주차는 자동으로 마무리된다. UI는 갑작스러운 차단처럼 보이지 않도록, "늦은 시간이 되어 기숙사로 돌아간다"는 짧은 전환 문구 또는 화면을 보여준 뒤 바로 다음 주 준비 화면으로 넘어간다. 별도의 주간 요약은 여기서 보여주지 않고, 전체 14주 종료 후 Memory Recap에서 누적 회고를 보여준다.

### 9.2 에너지

에너지는 플레이어의 신체적/정서적 여유를 표현한다. 이동, 운동 관련 이벤트, 긴 탐색, 사회적 활동 등에 사용된다. 휴식 이벤트나 음식 이벤트로 회복할 수 있다.

최종 게임의 에너지는 0-10 범위의 작은 수치로 관리한다. 이 범위는 플레이어가 현재 상태를 직관적으로 이해하기 쉽고, 이벤트 선택지 비용을 작게 설계하기에 적합하다.

권장 사용 방식:

| 상황 | 에너지 비용/효과 예시 |
| --- | --- |
| 가벼운 대화, 짧은 관찰 | 0-1 |
| 일반 탐색, 짧은 이동 피로 | 1 |
| 운동, 긴 산책, 적극적 참여 | 2-3 |
| 매우 피곤한 활동 또는 장시간 이벤트 | 3 이상 |
| 휴식, 식사, 조용한 회복 이벤트 | +1에서 +3 |

에너지는 시간과 다르게 회복 가능하다. 다만 회복에는 보통 시간 또는 돈이 함께 들어가야 한다. 예를 들어 카페에서 쉬면 시간 1시간과 돈을 쓰고 에너지를 회복할 수 있으며, 벤치에서 쉬면 돈은 쓰지 않지만 회복량이 낮을 수 있다.

결정 필요:

- 에너지 시작값과 주간 회복 규칙은 다음 팀이 이벤트 설계와 플레이 테스트를 통해 조정해야 한다.
- 에너지가 0이면 에너지를 요구하는 이벤트 선택지는 제한된다. 시간만 요구하는 이벤트는 계속 선택할 수 있다.

### 9.3 돈

돈은 카페, 교통, 행사비, 음식, 클럽 활동, 장비 대여 같은 선택지에 사용된다. 돈은 더 좋은 선택지를 열 수 있지만, 돈을 쓰지 않는 선택지도 항상 의미가 있어야 한다.

돈은 매주 새로 지급되는 주간 예산형 자원으로 관리한다. 즉, 플레이어는 매주 제한된 예산 안에서 어떤 경험에 돈을 쓸지 선택한다. 이 구조는 실제 학생 생활의 감각과 잘 맞는다. 한 주의 돈은 그 주의 선택 압력을 만들고, 다음 주에는 새 예산으로 다시 시작한다.

권장 사용 방식:

| 상황 | 돈 비용/효과 예시 |
| --- | --- |
| 무료 활동, 공공 장소 탐험 | $0 |
| 저렴한 간식, 대중교통, 간단한 준비물 | 낮은 비용 |
| 카페, 행사 참가, 장비 대여 | 중간 비용 |
| 특별 이벤트, 큰 외출, 여러 사람과의 활동 | 높은 비용 |

돈을 쓰는 선택지는 빠른 해결, 높은 에너지 회복, 특정 정보 접근, 사회적 편의 같은 장점을 줄 수 있다. 그러나 돈이 없는 플레이어도 의미 있는 선택을 할 수 있어야 한다. 무료 선택지는 느리거나 에너지 비용이 높을 수 있지만, 서사적으로 열등하게 보이면 안 된다.

결정 필요:

- 돈의 주간 기본 지급량과 이벤트별 가격표는 다음 팀이 콘텐츠 수량, 평균 이동량, 회복 이벤트 빈도를 보고 조정해야 한다.
- 돈이 부족한 플레이어가 소외되지 않도록 무료/저비용 선택지의 설계 원칙을 계속 유지해야 한다.

## 10. 보물 시스템

### 10.1 보물의 철학적 정의

보물은 ANU 캠퍼스에서 의미를 전달하는 발견 단위다. 보물은 물건, 장소, 경험, 사람과의 연결, 역사적 이야기, 자연 현상, 학생 문화, 유저가 남긴 기억일 수 있다.

### 10.2 제작용 보물 분류

최종 콘텐츠 제작을 위해 보물은 다음 유형으로 분류한다.

| 유형 | 설명 | 예시 |
| --- | --- | --- |
| Place Treasure | 장소 자체의 의미를 발견하는 보물 | 도서관, 코트, 숨은 정원 |
| History Treasure | 캠퍼스의 역사, 유산, 기록과 연결된 보물 | 건축물, 기념물, 오래된 시설 |
| Seasonal Treasure | 특정 계절, 시간, 날씨, 자연 현상과 연결된 보물 | 꽃, 동물, 낙엽, 특정 시기 행사 |
| Social Treasure | 사람, 친구, 클럽, 공동체 활동과 연결된 보물 | 보드게임 모임, 스포츠 활동 |
| Support Treasure | 학생 지원, 생활 정보, 생존 지식과 연결된 보물 | 무료 식사, 상담, 학습 지원 |
| Personal Memory | 플레이어의 선택으로 만들어진 개인적 추억 | 친구와 함께한 사건, 도움을 준 순간 |
| Legacy Treasure | 다른 플레이어가 공유한 힌트를 통해 발견하는 보물 | 이전 플레이어의 SNS 힌트 |

### 10.3 보물 상태 정의

보물과 이벤트는 같은 것이 아니다. 최종 게임은 다음 상태를 분리해서 저장해야 한다.

| 상태 | 의미 |
| --- | --- |
| Seen | 이벤트가 화면에 표시되어 플레이어가 해당 이벤트를 본 상태 |
| Experienced | 플레이어가 선택지를 고르고 결과 문장을 끝까지 읽은 상태 |
| Resolved | 플레이어가 이벤트 결말을 본 상태 |
| Found | 플레이어가 이벤트 결과로 보물을 발견한 상태 |
| Collected | 플레이어가 보물을 도감에 소장한 상태 |
| Shared | 플레이어가 보물을 도감에 넣지 않고 다른 플레이어에게 힌트로 남긴 상태 |
| Missed | 플레이어가 보물 발견 기회를 놓쳤지만 재방문 가능성이 남은 상태 |
| Retry Available | 플레이어가 놓친 이벤트를 이번 회차에서 다시 시도할 수 있는 상태 |
| Locked Out | 해당 회차에서 다시 얻을 수 없는 상태 |

확정된 상태 기록 규칙:

- 이벤트가 화면에 뜬 순간 `Seen`으로 기록한다.
- 플레이어가 선택지를 고르고 결과 문장을 끝까지 읽은 순간 `Experienced`로 기록한다.
- 보물을 발견했지만 share한 경우, `Found`와 `Shared`를 모두 기록한다.
- 실패 선택지를 골랐지만 재시도가 가능한 경우, `Missed`와 `Retry Available`을 기록한다.
- 보물을 share한 경우, 해당 보물은 이번 회차에서 다시 얻을 수 없도록 `Locked Out`으로 기록한다.
- 엔딩에서는 collected와 shared를 모두 중요한 선택으로 다룬다.

이 상태들은 서로 배타적인 하나의 값으로만 저장하지 않는 것이 좋다. 하나의 이벤트 기록은 `Seen + Experienced + Found + Shared + Locked Out`처럼 여러 상태를 동시에 가질 수 있다. 이렇게 해야 엔딩에서 "발견했지만 남에게 남긴 보물"과 "도감에 간직한 보물"을 분리해서 보여줄 수 있다.

## 11. Collect / Share 시스템

### 11.1 Collect

Collect는 플레이어가 보물을 자기 도감에 소장하는 선택이다.

결과:

- 보물이 Investigator Card 또는 Collection Book에 등록된다.
- 보물 이미지, 이름, 설명, 관련 장소, 발견 주차가 저장된다.
- 엔딩 회고에서 "내가 간직한 보물"로 등장한다.

### 11.2 Share

Share는 플레이어가 보물을 자기 도감에 넣지 않고, 다른 플레이어에게 힌트로 남기는 선택이다.

결과:

- 해당 보물은 이번 회차 도감에 수집되지 않는다.
- 플레이어는 이미 이벤트를 경험했으므로, 보물의 의미와 장면 자체는 Memory Ledger에 남는다.
- 해당 이벤트는 완료 처리되어 같은 회차에서 다시 획득할 수 없다.
- Supabase에 share record가 저장된다.
- 다른 플레이어의 in-game social media feed에 이전 플레이어의 post 형태로 노출될 수 있다.
- 엔딩 회고에서 "내가 남긴 legacy"로 등장한다.

### 11.3 Share의 감정 보상

Share 선택은 단순한 손해가 아니라 유산으로 느껴져야 한다. 엔딩에서는 다음과 같은 문장 구조를 사용할 수 있다.

예시:

> 당신은 Lemon Tree를 가져가지 않았다. 대신 누군가가 힘든 날 혼자 걷지 않도록, 작은 힌트를 캠퍼스에 남겼다.

## 12. Clue 시스템

Clue는 플레이어가 특정 보물이나 이벤트를 찾을 가능성을 높이는 정보 단위다. Clue는 다음 경로로 획득할 수 있다.

- 친구의 social media post
- 다른 플레이어가 남긴 shared post
- 이벤트 본문 안의 clickable keyword
- QR 코드 또는 캠퍼스 현장 단서
- 친구와의 대화
- 이전 이벤트의 실패/힌트 선택지

Clue 획득 효과:

- 지도에 pin이 표시된다.
- 관련 위치의 hover 정보에 clue 표시가 추가된다.
- 해당 위치 탐험 시 관련 이벤트 trigger chance가 증가하거나 확정된다.
- 특정 선택지가 unlocked될 수 있다.

결정 필요:

- clue가 이벤트를 확정 발동시키는지, 확률만 높이는지 최종 규칙이 필요하다.
- clue pin이 정확한 위치를 알려주는지, 대략적인 지역만 알려주는지 결정해야 한다.

## 13. Friend / Trait 시스템

### 13.1 친구의 역할

친구는 단순한 보너스가 아니라 플레이어의 캠퍼스 경험을 다르게 해석하게 만드는 동행자다.

MVP 구현에서 친구는 주간 trait 제공자와 clue source로 남겨도 된다. 이 경우 친구 시스템의 목적은 플레이어가 매주 다른 탐험 전략을 선택하게 만드는 것이다.

확장 구현에서 친구는 짧은 개인 서사, 관계 변화, 반복 등장 이벤트, 엔딩 회고 문장을 가질 수 있다. 이 경우 친구 시스템의 목적은 캠퍼스가 장소의 집합이 아니라 사람과의 관계망으로 느껴지게 만드는 것이다.

공통 기능:

- 주간 시작 시 최대 2명까지 선택 가능
- trait 제공
- 특정 이벤트 선택지 unlock
- social media clue post 제공
- 엔딩 회고에 등장
- 특정 보물에 대한 다른 관점 제공

### 13.2 Trait의 역할

Trait는 플레이어와 친구가 가진 탐험 성향 또는 전문성이다. 각 treasure와 event는 tag를 가지며, trait와 tag가 맞으면 탐험 효율이나 선택지가 달라진다.

예시 trait:

| Trait | 효과 예시 |
| --- | --- |
| History Enthusiast | History Treasure 관련 clue 해석 또는 성공 확률 증가 |
| Athlete | 이동 또는 운동 이벤트의 에너지 비용 감소 |
| Social Connector | 친구/클럽 관련 이벤트 선택지 unlock |
| Nature Observer | Seasonal Treasure 발견 확률 증가 |
| Budget Planner | 돈 관련 선택지 비용 감소 또는 무료 대안 발견 |
| Night Owl | 늦은 시간대 이벤트 발견 가능 |

결정 필요:

- 플레이어 major와 trait를 어떻게 연결할지 정해야 한다.
- 다음 팀은 범위에 따라 MVP형 친구 시스템과 확장형 친구 시스템 중 하나를 선택해야 한다.

## 14. Event 시스템

### 14.1 이벤트의 역할

이벤트는 보물을 전달하는 주된 내러티브 단위다. 이벤트는 단순 퀴즈가 아니라 플레이어가 장소를 어떻게 읽는지 시험하는 작은 장면이어야 한다.

### 14.2 이벤트 기본 구조

각 이벤트는 다음 요소를 가져야 한다.

- event_id
- title
- location_id
- location availability compatibility
- week availability
- time-of-day availability
- treasure_id
- treasure_type
- tags
- source type
- evidence note
- narrative intro
- choices
- choice costs
- choice requirements
- outcome texts
- result state
- collect/share availability
- re-trigger rule
- ending memory text
- asset references

이벤트를 추가할 때는 반드시 해당 event의 `time-of-day availability`가 location의 접근 가능 시간과 충돌하지 않는지 확인해야 한다. 예를 들어 어떤 location이 저녁에 닫혀 있다면, 그 location에는 `evening_only` 이벤트를 배치하지 않는다.

### 14.3 선택지 원칙

각 이벤트는 최소 3개 선택지를 권장한다.

- A: 깊이 관찰하거나 적극적으로 참여해 보물을 발견하는 선택
- B: 피상적으로 지나가거나 서두르며 기회를 놓치는 선택
- C: 완전한 성공은 아니지만 clue, 재방문 가능성, 관계 변화, trigger boost를 얻는 선택

주의:

- B 선택지도 플레이어를 조롱하면 안 된다.
- 실패는 처벌이 아니라 "다른 학기 이야기"가 되어야 한다.
- C 선택지는 share 시스템과 잘 연결될 수 있다.

## 15. Social Media 시스템

게임 안의 social media는 phone UI로 접근한다. 이 시스템은 단순 메뉴가 아니라 clue, 친구, legacy가 만나는 공간이다.

기능:

- 친구들의 주간 post 표시
- clickable keyword를 통한 clue 획득
- 이전 플레이어가 공유한 treasure hint post 표시
- 플레이어가 share한 보물의 post 생성
- QR 코드 또는 외부 캠퍼스 활동 연결 가능

최종 구현:

- 로컬 기본 post와 Supabase에서 가져온 shared post를 함께 feed에 표시한다.
- shared post는 랜덤 확률 또는 조건부 추천으로 노출한다.
- post는 author_name, avatar, text, image, clue annotation, shared_treasure_id를 포함한다.
- MVP에서는 플레이어가 완전한 자유 문장을 작성하지 않고, 미리 준비된 키워드와 문장 템플릿을 조합해 shared post를 만든다. 이 방식은 Dark Souls/Elden Ring의 메시지 시스템처럼 표현 자유를 주되 부적절한 문구 위험을 줄인다.
- 확장 구현에서는 부적절한 내용 필터링, 신고, 검수 흐름이 준비된 경우에 한해 플레이어 직접 문구 저장을 고려할 수 있다.

결정 필요:

- 다른 플레이어의 share post가 얼마나 자주 노출될지 정해야 한다.
- 동일 보물에 대한 여러 share post 중 어떤 것을 보여줄지 규칙이 필요하다.
- MVP moderation은 금칙어 또는 특정 단어 필터링을 기본으로 한다.

## 16. Memory Ledger

Memory Ledger는 쉽게 말해 개인 저장 파일 안에 들어 있는 "플레이어의 학기 일지"다. 게임은 플레이어가 어떤 이벤트를 봤고, 어떤 선택을 했고, 어떤 보물을 수집하거나 공유했는지를 이 일지에 차곡차곡 적어 둔다. 14주가 끝나면 엔딩 회고 화면은 이 기록을 읽어서 플레이어의 캠퍼스 이야기를 다시 보여준다.

Memory Ledger는 서버에 올리는 공개 기록이 아니다. 개인 진행 기록과 엔딩 회고용 기록은 개인 저장 파일에 저장한다. 다만 플레이어가 보물을 Share해서 다른 플레이어에게 힌트를 남기는 경우, 다른 플레이어에게 보여줄 shared post/hint만 Supabase 서버에 저장한다.

예시:

- `Lemon Tree` 이벤트를 화면에 띄웠다는 기록: 개인 저장 파일
- `Lemon Tree`를 Share해서 이번 회차에서 다시 못 얻는다는 기록: 개인 저장 파일
- 다른 플레이어에게 보여줄 `Lemon Tree` 힌트 글: Supabase 서버
- 엔딩에서 "당신은 Lemon Tree를 다른 학생에게 남겼습니다"라고 보여주기 위한 기록: 개인 저장 파일의 Memory Ledger

최종 엔딩을 만들기 위해 게임은 모든 중요한 경험을 Memory Ledger에 기록해야 한다. 이 기록은 단순 저장 데이터가 아니라 엔딩 회고의 원재료다.

권장 필드:

| 필드 | 설명 |
| --- | --- |
| memory_id | 고유 기록 id |
| week | 발생 주차 |
| location_id | 장소 |
| event_id | 이벤트 |
| treasure_id | 관련 보물 |
| states | Seen, Experienced, Found, Collected, Shared, Missed, Retry Available, Locked Out 등 복수 상태 |
| choice_key | 선택지 |
| choice_label | 선택지 문구 |
| result_state | collected/shared/missed/clue/friend 등 |
| resource_spent | 시간/에너지/돈 사용량 |
| friends_present | 함께한 친구 목록 |
| traits_used | 사용된 trait |
| emotional_tags | wonder, warmth, curiosity, generosity 등 |
| recap_text | 엔딩 회고용 문장 |
| legacy_record_id | share와 연결된 외부 record id |

## 17. 엔딩 회고

14주가 끝나면 게임은 플레이어의 학기를 회상 형식으로 보여준다.

엔딩의 최종 표현 방식은 다음 팀이 제작 범위와 UI 역량에 맞춰 선택한다. 사진첩, SNS 타임라인, 지도 경로 재생, 편지, 크레딧 롤 중 어떤 형식도 가능하다. 중요한 것은 형식 자체가 아니라, 플레이어의 실제 선택 기록이 회고의 원재료가 되어야 한다는 점이다.

권장 구조:

1. 학기 종료 메시지
2. 지도 위 방문 경로 또는 주요 장소 하이라이트
3. 내가 수집한 보물
4. 내가 공유한 legacy
5. 내가 만난 친구
6. 내가 놓쳤지만 기억에 남은 순간
7. 플레이 스타일 요약
8. 개발자 credit

### 17.1 플레이 스타일 요약

점수 대신 플레이어의 경향을 해석한다.

예시 profile:

| Profile | 조건 예시 | 의미 |
| --- | --- | --- |
| The Explorer | 방문 장소 수와 clue follow 수가 높음 | 캠퍼스를 넓게 탐험한 플레이어 |
| The Archivist | History/Place treasure 수집 비중이 높음 | 장소의 기록과 유산을 붙잡은 플레이어 |
| The Connector | 친구 이벤트와 social treasure 비중이 높음 | 사람을 통해 캠퍼스를 이해한 플레이어 |
| The Caretaker | share/legacy 선택 비중이 높음 | 자기 경험을 다음 사람에게 남긴 플레이어 |
| The Local | 반복 방문과 재시도 이벤트가 많음 | 한 장소를 천천히 자기 것으로 만든 플레이어 |

## 18. 콘텐츠 확장 원칙

Treasure는 제한 없이 추가될 수 있다. 그러나 제작 품질을 유지하려면 모든 보물은 다음 조건을 만족해야 한다.

- ANU 캠퍼스 또는 ANU 생활과 명확히 연결된다.
- 플레이어에게 의미 있는 감정 또는 정보를 전달한다.
- 장소, 시간, 사람, 선택 중 최소 하나와 연결된다.
- 이벤트, clue, asset, ending text를 함께 가진다.
- 사실 기반 콘텐츠라면 source/evidence note를 포함한다.
- 개인적 이야기나 유저 생성 콘텐츠라면 "personal story" 또는 "community contribution"으로 구분한다.

출시 시점의 보물 최소 수량은 고정하지 않는다. 다만 게임이 14주 동안 지속되는 구조이므로, 각 주차의 각 active location node에는 플레이어가 경험할 수 있는 이벤트가 최소 하나 이상 남아 있어야 한다. 시간대별 접근 제한이 있는 location의 경우, 접근 가능한 시간대 안에서 최소 이벤트 커버리지를 판단한다. 이 원칙은 플레이어가 후반 주차에 특정 노드를 방문했을 때 아무 일도 일어나지 않는 빈 지도를 방지하기 위한 것이다.

## 19. 사실성 및 콘텐츠 신뢰 정책

이 게임은 실제 캠퍼스 정보와 개인적 이야기, 창작된 내러티브가 섞일 수 있다. 다음 팀은 콘텐츠 신뢰 구분을 데이터에 포함해야 한다.

권장 source_type:

| source_type | 의미 |
| --- | --- |
| official | ANU 공식 정보 또는 공식 기관 자료 기반 |
| observed | 팀 또는 contributor가 직접 관찰한 캠퍼스 경험 |
| community_story | 학생/교직원/플레이어가 제공한 개인적 이야기 |
| fictionalised | 실제 장소를 바탕으로 게임적 각색을 더한 이야기 |
| legacy_user_generated | 이전 플레이어의 share로 생성된 힌트 |

주의:

- 역사, 제도, 지원 서비스, 안전 정보는 official 또는 검증된 자료가 필요하다.
- 개인적 이야기와 창작 각색은 사실 주장처럼 보이면 안 된다.
- 유저 생성 힌트는 moderation과 신고 흐름이 필요하다.

## 20. 결정된 사항과 남은 질문

### 20.1 결정된 사항

| 항목 | 결정 |
| --- | --- |
| 시간대별 접근 제한 | 우선 location 단위에 둔다. sub-node 구현 후에는 sub-node 단위로 확장할 수 있다. |
| 이벤트/접근성 충돌 방지 | 특정 시간에 접근할 수 없는 location에는 그 시간대에만 경험 가능한 이벤트를 배치하지 않는다. |
| 24:00 전환 | 별도 주간 요약 없이 자연스럽게 집/기숙사로 돌아가며 다음 주 준비 화면으로 넘어간다. |
| 지도 계층 전환 | 다음 팀이 이벤트를 추가하면서 맵 확장의 필요를 느낄 때 region/location/sub-node 구조로 전환한다. |
| 엔딩 UI | 사진첩, SNS 타임라인, 지도 경로 재생, 편지, 크레딧 롤 중 다음 팀이 원하는 형식을 선택할 수 있다. |
| 친구 시스템 범위 | 기본은 힌트 제공과 이동 이득이다. 확장 시 대사 변화, 이벤트 결말 변화, 개인 서사, 관계 변화를 추가할 수 있다. |
| 에너지 0 처리 | 시간만 소모하는 이벤트는 가능하지만, 에너지를 요구하는 이벤트 선택지는 제한된다. |
| 돈 밸런싱 | 주간 기본 지급량과 가격표는 다음 팀의 이벤트 설계에 따라 조정한다. |
| Shared post 입력 | MVP는 키워드 기반 템플릿을 우선한다. 필터링/검수 역량이 있으면 플레이어 직접 문구 저장을 고려한다. |
| Moderation MVP | 금칙어 또는 특정 단어 필터링으로 시작한다. |
| 콘텐츠 최소 수량 | 고정 수량은 없다. 단, 각 주차의 각 active location node에는 접근 가능한 시간대 기준으로 경험 가능한 이벤트가 최소 하나 이상 남아 있어야 한다. |
| 이벤트 상태 기록 | 이벤트가 화면에 표시되면 Seen, 선택지를 골라 끝까지 읽으면 Experienced로 기록한다. |
| 보물 발견/공유 기록 | 보물을 발견한 뒤 Share하면 Found와 Shared를 모두 기록한다. |
| 실패/재시도 기록 | 실패 선택지를 골랐지만 재방문 가능한 경우 Missed와 Retry Available로 남긴다. |
| Share 잠금 | Share한 보물은 이번 회차에서 다시 얻을 수 없도록 Locked Out 처리한다. |
| 개인 진행 저장 위치 | 이벤트 Seen/Experienced, 보물 Found/Collected/Shared/Locked Out 상태는 개인 저장 파일에 저장한다. |
| Supabase 저장 범위 | 다른 플레이어에게 노출할 shared post/hint만 Supabase 서버에 저장한다. |
| 엔딩 회고 데이터 | 엔딩 회고는 개인 저장 파일 안의 Memory Ledger를 읽어서 구성한다. |

### 20.2 남은 핵심 질문

현재 큰 방향은 결정되었다. 남은 일은 다음 팀이 이 결정을 실제 데이터 필드와 저장 형식으로 옮기는 것이다. 즉, 개인 저장 파일 안에 어떤 배열/딕셔너리 구조로 Memory Ledger를 넣을지, Supabase shared post table에는 어떤 컬럼을 둘지, 엔딩 화면은 그 기록을 어떤 순서로 읽을지를 구현 단계에서 정하면 된다.

## 21. 다음 팀을 위한 구현 우선순위

1. 개인 저장 파일 안에 Memory Ledger 데이터 구조 추가
2. 이벤트/보물 상태를 복수 상태로 분리 저장
3. 08:00-24:00, 1시간 단위 기반 시간 엔진 구현
4. location 단위 시간대별 접근 조건 추가
5. 에너지 0-10 범위와 주간 예산형 돈 시스템에 맞춰 이벤트 비용표 설계
6. 이벤트 시간 조건과 location 접근 가능 시간의 충돌 검증 추가
7. 친구/trait 데이터 구조 확장
8. Supabase 기반 shared post/hint 저장/조회
9. 키워드 기반 shared post 템플릿과 MVP 금칙어 필터 구현
10. 엔딩 회고 화면 구현
11. 콘텐츠 source_type 및 moderation 정책 추가
12. 보물/이벤트 제작 템플릿 문서화
13. 각 주차/active location node의 이벤트 커버리지 검증 추가
